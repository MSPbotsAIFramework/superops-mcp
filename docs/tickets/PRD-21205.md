## Requirement understanding

One line: Unified PSA+RMM platform integration for SuperOps — tickets, assets, automation, and client management.

The ticket is a generic feature listing for the SuperOps.ai connector (PSA+RMM platform), copied
from the Conduit marketplace listing linked in the description (`https://conduit.wyre.ai/plugins/superops`).
It names four capability areas — tickets, assets, automation, client management — without pointing
at a specific bug, a specific missing tool, or a specific workflow. There is no other requester
comment on the ticket beyond the design-leg claim comment.

## Current state (every claim carries path:line)

`MSPbotsAIFramework/superops-mcp` already exists and is the only SuperOps repository in the
organization (checked: `superops`, `superops-connector`, `super-ops-mcp`, `superops-integration`,
`wyre-superops-mcp` all 404). It is a working MCP server for SuperOps's MSP GraphQL API
(`README.md:1-13`), already covering three of the four capability areas the ticket names:

- **Clients** — list / get / search (`src/superops_mcp/tools/clients.py`, registered
  `src/superops_mcp/tools/navigation.py:26-29`).
- **Tickets** — list / get / create / update / add note / log time (`src/superops_mcp/tools/tickets.py`,
  `navigation.py:30-40`).
- **Assets** — list / get / software / patches (`src/superops_mcp/tools/assets.py:88-183`,
  `navigation.py:41-44`).
- **Technicians**, plus a raw-GraphQL escape hatch (`superops_custom_query` / `superops_custom_mutation`,
  `navigation.py:45-57`).

**Automation is not covered by a named tool.** `DOMAINS` in `navigation.py:25-58` has no
`automation` entry, and there is no `scripts.py` / `automation.py` / `policies.py` module under
`src/superops_mcp/tools/`. The only way to reach SuperOps script or alert operations today is the
generic `superops_custom_query` / `superops_custom_mutation` pair, which requires the calling agent
to already know the right GraphQL document — unlike every other capability area, which has a
curated, parameter-validated tool. Per the design-leg rule for this situation ("unsure whether a
capability is covered → treat it as not covered"), this is treated as a real gap, not a shortcut
to "already available."

The connector is already registered in the Agent Platform's connector field index as
`SuperOps.ai — API Token* (masked), Subdomain*` (wiki: `ProductDocs/_connector-fields.md` §83,
row "SuperOps.ai", synced 2026-10-30), matching the two required headers this repo already reads
(`src/superops_mcp/tools/_common.py:31-34`). wiki does not cover SuperOps feature scope beyond the
credential-field listing — `wiki find "superops"` has no other hits (checked 2026-10-30, product
version v20261028.0919); treated as "wiki does not cover SuperOps capability scope" rather than
silently skipped.

SuperOps's public GraphQL API reference (`developer.superops.com/msp/`, fetched 2026-10-30) names
script and alert operations that are not in this repo's tool table: `getScriptList`,
`getScriptListByType`, `runScriptOnAsset`, `getAlertList`, `getAlertsForAsset`, `createAlert`,
`resolveAlerts`. This page is a documentation index, not the literal schema (SDL) — it is cited
here only to establish that these capabilities exist, not to pin the exact field names, which the
implementer must re-verify against the published schema before writing the GraphQL documents
(README.md:235-236 describes the same discipline for the existing tools: "every GraphQL document
was validated against the SuperOps MSP schema").

## Product design

### Goals / Non-goals

**Goals**

- Add an `automation` capability area to the SuperOps connector so an agent can (a) see what
  scripts are available to run on a managed asset, (b) run one on explicit request, (c) see what
  alerts are open (tenant-wide or for one asset), and (d) mark alert(s) resolved on explicit
  request — closing the gap between what the ticket's capability list names and what the connector
  currently exposes as named tools.
- Keep the new tools consistent with the existing four areas: same pagination shape
  (`page`/`pageSize`/`cursor`/`offset`, `listInfo` with `hasMore: null` on the last page), same
  error envelope, same "write tools only on explicit request" convention.

**Non-goals**

- Creating or editing alert *rules* / monitoring *policies* (SuperOps's `createAlert` mutation
  creates an alert record, not a monitoring policy). The ticket does not ask for policy
  authoring, and letting an agent originate monitoring alerts is a materially different risk
  (synthetic alerts polluting a tenant's monitoring feed) from reading and acting on alerts that
  already exist. Left out of this round; a future ticket can add it if a concrete need shows up.
- Scheduling or recurring script deployment (SuperOps "automation policies" that run scripts on a
  schedule or on an event trigger) — not named in the ticket and not in the four-area description;
  out of scope.
- Any change to the Agent Platform's connector registration UI or credential form — the connector
  is already registered (current state, above); this ticket only adds tools inside the existing
  MCP server.

### Acceptance criteria AC1..AC7

- **AC1** — Given valid `X-SuperOps-API-Token` and `X-SuperOps-Subdomain` headers, when the agent
  calls `superops_navigate(domain="automation")`, then the response names the new automation tools
  (script list/run, alert list/resolve) without making any upstream SuperOps call, the same way
  `superops_navigate` already behaves for the other four domains.
- **AC2** — Given valid credentials, when the agent calls the scripts-list tool (optionally
  filtered by script type), then it returns a paginated list of scripts available to the tenant,
  using the same `page`/`pageSize`/`listInfo` shape as the existing list tools.
- **AC3** — Given valid credentials, an existing asset id and an existing script id, when the agent
  calls the scripts-run tool, then the script run is dispatched against that asset and the tool
  returns a confirmation / run reference; the tool's own description tells the agent to call it
  only on the user's explicit request (same convention as `superops_tickets_create` et al.).
- **AC4** — Given a missing or unknown `assetId` or `scriptId`, when the agent calls the scripts-run
  tool, then the call fails with `invalid_argument` and no script is dispatched.
- **AC5** — Given valid credentials, when the agent calls the alerts-list tool (tenant-wide, or
  scoped to one `assetId`), then it returns a paginated list of alerts using the same list shape as
  the existing tools.
- **AC6** — Given valid credentials and one or more alert ids, when the agent calls the
  alerts-resolve tool, then those alerts are marked resolved; resolving an alert that is already
  resolved is a no-op, not an error (idempotent, matching `superops_tickets_update`'s annotation
  style).
- **AC7** (auth / multi-tenant, required by the design SOP's "at least one permission case, hit the
  backend" rule) — Given a request to any new automation tool without the required headers, then
  the existing gateway middleware (`_common.py:93-146`) rejects it with 401 before any tool code
  runs — no change needed there, but it must be exercised for the new tools too. Given two
  different tenants' credentials, each tenant only ever sees its own scripts/alerts/assets, because
  every call carries that request's header-scoped token and the server holds no cross-request
  cache or state (`_common.py:41-46` — the existing per-request isolation contract, unchanged by
  this ticket).

### Open questions

- **"Automation" is read as "run an existing script, see and resolve alerts."** SuperOps's API
  also has alert-rule creation and scheduled/policy-based automation (Non-goals, above). If product
  actually meant something narrower (e.g., alert visibility only, no script execution) or broader
  (policy authoring), the scope here should be revisited. **Not blocking**: trimming or dropping
  the scripts-run tool later is a one-file, no-migration change with no data impact, so proceeding
  on this assumption does not risk the rest of the ticket. Flagged for product/BA to confirm when
  this reaches INT acceptance.
- **Exact GraphQL field/argument names** for the script and alert operations are taken from
  SuperOps's documentation index, not the literal schema (Current state, above). Not blocking —
  this is the same verification step every existing tool in this repo already goes through before
  its GraphQL document is written; it does not change the tool surface (names, parameters, return
  shape) fixed by this design.

## Tech design

### Conclusion

Add one new tool module (`src/superops_mcp/tools/automation.py`) exposing four new tools —
scripts list, scripts run, alerts list, alerts resolve — registered the same way every other
domain module is registered. Extend `superops_navigate`'s domain enum with `automation`. No
changes to `api_client.py`, the credential middleware, or any existing tool's behavior or
parameters.

### Where the current implementation lives

- Domain registry and `superops_navigate`: `src/superops_mcp/tools/navigation.py:25-72`.
- Module registration list: `src/superops_mcp/server.py:162-165`.
- Shared pagination / error-envelope / write-annotation helpers: `src/superops_mcp/tools/_common.py`
  (`READ_ONLY`, `WRITES`, `WRITES_IDEMPOTENT`, `ANY_WRITE` at `:31-36`; `list_input`/`page_result`/
  `locate`/`paging` at `:83-145`; `run_tool` error wrapper at `:170-199`).
- Closest existing precedent for a list+get-by-id module with one filtered list tool:
  `src/superops_mcp/tools/assets.py:88-183` (same `page`/`pageSize`/`cursor`/`offset` parameters,
  same `page_result` usage).
- Closest existing precedent for a write tool with an explicit-request-only description and a
  non-idempotent annotation: `src/superops_mcp/tools/tickets.py:285-339` (`superops_tickets_create`,
  `WRITES` annotation).

### Option analysis

- **New `automation.py` module registered alongside the existing four (chosen)** — matches the
  repo's existing one-module-per-domain convention exactly; `tools/__init__.py:14` already
  documents the contract every module follows (`register(mcp, client_factory)`); zero risk to
  existing tools.
- **Add script/alert tools to an existing module (e.g. `assets.py`, since scripts/alerts are
  asset-scoped)** — rejected: alerts here are not asset-scoped (tenant-wide list exists too,
  `getAlertList` vs `getAlertsForAsset`), and mixing two GraphQL entity families into one file
  breaks the one-domain-per-file convention the repo uses everywhere else (confirmed by reading
  `tools/__init__.py` and all five existing tool files).
  Rejected
- **Tell the agent to use `superops_custom_query` / `superops_custom_mutation` for automation and
  write no new code** — this is the status quo and is what the design's Current-state section
  already determined does *not* count as "covered": the agent would have to construct the correct
  GraphQL document itself with no parameter validation, unlike every other capability area.
  Rejected as it does not close the gap the ticket names.

### Data & API contract

New tools (all under the `automation` domain), same error envelope as every existing tool
(`{"error": {"code": ..., "message": ..., "retryable": ...}}`, `_common.py` / `README.md:176-185`):

- **`superops_automation_scripts_list`** (`READ_ONLY`) — params: `scriptType` (optional string,
  maps to `getScriptListByType` when given, `getScriptList` otherwise), `page`, `pageSize`, `max`,
  `cursor`, `offset` (same aliasing as the existing list tools). Returns `{scripts: [...], listInfo,
  offset, next_offset}` — one list item per script (id, name, type, description — exact fields
  confirmed against schema at implementation time).
- **`superops_automation_scripts_run`** (write, `ANY_WRITE` — destructive-capable: a script can run
  arbitrary commands on the target endpoint, same risk class as `superops_custom_mutation`) —
  params: **`scriptId`** (required), **`assetId`** (required). Returns a run/job reference. Docstring:
  "Runs a script on a managed endpoint. Call only when the user explicitly asks for this script to
  run on this asset." Not retried automatically on failure (same policy as other write mutations:
  retried only on rate limiting — README.md:184-185).
- **`superops_automation_alerts_list`** (`READ_ONLY`) — params: `assetId` (optional — omitted means
  tenant-wide via `getAlertList`, given means `getAlertsForAsset`), `status`/`severity` filters if
  the schema exposes them (confirmed at implementation time), `page`, `pageSize`, `cursor`, `max`,
  `offset`. Returns `{alerts: [...], listInfo, offset, next_offset}`.
- **`superops_automation_alerts_resolve`** (write, `WRITES_IDEMPOTENT` — resolving an
  already-resolved alert is a no-op) — params: **`alertIds`** (required, list of one or more ids).
  Returns the resolved alert ids. Docstring: "Marks the given alert(s) resolved. Call only when the
  user explicitly asks."

Backward compatibility: all four tools are new; `superops_navigate`'s domain literal gains a value
additively. No existing tool's parameters, return shape, or error codes change.

### Key flow / sequence

1. Agent calls `superops_navigate(domain="automation")` to discover the four tools (no API call,
   mirrors the existing `navigation.py:69-72` behavior).
2. Agent calls `superops_automation_scripts_list` (or `_alerts_list`) to find a script id / alert
   id, same discovery pattern as `superops_clients_search` → `superops_tickets_list` in the
   repo's existing `INSTRUCTIONS` text (`_common.py:49-66`).
3. On the user's explicit request, agent calls `superops_automation_scripts_run` (or
   `_alerts_resolve`); the shared `run_tool` wrapper (`_common.py:170-199`) resolves per-request
   credentials, runs the GraphQL call, and converts any `SuperOpsError` / `ValueError` /unexpected
   exception into the standard error envelope — unchanged code path, no new error handling needed.

### Non-functional

- **Multi-tenant isolation**: unchanged architecture — credentials come from the per-request
  `contextvars` set by `GatewayCredentialsMiddleware` (`_common.py:93-146`) and are never cached
  or shared across requests; the new tools read that same context through `client_factory`, so
  there is no new place a cross-tenant leak could be introduced.
  AC7.
- **Idempotency / retries**: scripts-run is not auto-retried (script execution must never run
  twice from a transient retry); alerts-resolve is naturally idempotent. Both match the existing
  mutation retry policy described in README.md:184-185 — no new retry logic to write.
- **Security**: scripts-run is annotated destructive (`ANY_WRITE`) so MCP clients that surface
  annotations can warn the user before calling it, same as `superops_custom_mutation` today;
  credentials are still read only from headers, never logged (existing middleware, unchanged).
- **Observability**: both new write tools log through the existing `run_tool` wrapper
  (`logger.info("tool=%s outcome=...")`, `_common.py:188-196`) — no new logging code needed, just
  calling `run_tool` like every other tool does.
- **Performance**: list tools use the same pagination discipline as the existing ones (default
  page size 50, max 100) — no unbounded-list risk introduced.

### Deviations from the design, and why

1. **Test file location.** The design's "Test strategy" named `tests/test_tools.py`, but that file is a tools/list schema snapshot (`EXPECTED_TOOLS`, annotations, description budget) with no mocked-upstream calls. The repo's actual "mocked `SuperOpsClient`, one happy path + one `invalid_argument` path" pattern the design describes lives in `tests/test_api_client.py` (the `Recorder` / `_call` helpers used by every other domain's business-logic tests). The new tools' business-logic tests run there instead; `test_tools.py` only got the schema-snapshot additions every new tool needs (`EXPECTED_TOOLS`, `test_navigate_describes_automation_domain`). `docs/tickets/PRD-21205.ac.json` has been updated to point at the actual test ids.
2. **`resolveAlerts`'s return shape.** The design assumed the mutation "returns the resolved alert ids." SuperOps's public GraphQL reference (`developer.superops.com/msp/`, checked 2026-10-30) documents `resolveAlerts(input: ResolveAlertInput): Boolean`. `superops_automation_alerts_resolve` now returns `{alertIds: <the ids given>, resolved: true}` once the boolean confirms success, and raises `upstream_error` if SuperOps returns a falsy value — this is a safer, schema-accurate implementation of the same AC6 behavior (resolving an already-resolved alert is still a no-op success, not an error), not a scope change.
3. **GraphQL leaf field names beyond `id`/`name`.** As flagged in the design's "Open questions" and "Risks & dependencies", the exact field names on `Script`/`Alert`/`RunScriptData` are not independently verified against a live tenant schema — SuperOps's public reference confirms the operation names and the input/return *type* names (`ListInfoInput`, `ScriptListByTypeInput`, `RunScriptInput`, `AssetDetailsListInput`, `ResolveAlertInput`) but not their field-level shape. The chosen field selections follow this repo's existing conventions (e.g. `AssetDetailsListInput`'s `{assetId, listInfo}` nesting, reused for `ScriptListByTypeInput`'s `{scriptType, listInfo}`) and are flagged in a code comment in `automation.py`. This does not block merge per `references/mcp-track.md` §3 ("no vendor test account is not a blocker") and is called out again here for the reviewer.

### Reuse and cleanup

No new dependency; reused `_common.py`'s pagination/condition/error helpers, annotation constants, `run_tool`, and the existing per-tool test infrastructure (`Recorder`/`_call`, `PAGED_TOOLS`) as designed.
